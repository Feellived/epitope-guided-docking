# 02. AF3 출력 처리

> ⚠️ **이 문서는 2026년 6월 시점 기준이며 이후 갱신하지 않았다.**
> 현재 파이프라인은 `pipeline/` 에 있다. 배경은 `legacy_af3/README.md` 참조.

AlphaFold3(이하 **AF3**)가 항체-항원 도킹을 돌리고 나면 폴더 하나에 여러 파일이 쏟아진다.
이 문서는 그 파일들이 각각 무엇인지, 우리 ML 파이프라인이 거기서 무엇을 꺼내 쓰는지,
그리고 우리 레포의 스크립트로 어떻게 처리하는지를 **초보가 직접 한 번씩 손으로 실행해보는 것**을
목표로 단계별로 정리한다.

전제:
- 레포 루트는 `~/projects/epitope-guided-docking` 이다. 아래 명령은 대부분 이 루트에서 실행한다고 가정한다.
- 파이썬 명령은 로컬 맥(zsh) 또는 연구실 리눅스 서버 어디서든 같다. 서버 접속·전송은 `docs/03_서버_ssh_scp_tmux.md` 참고.
- 도킹 입력을 넣을 때 **위=항원, 아래=항체** 순서로 넣고 그 위치를 기억하는 게 우리 관례다.
  그러면 결과에서 **chain A = 항원, chain B = 항체**로 일관되게 매핑된다.
  (단, 항체를 Fab/scFv로 넣으면 체인이 더 쪼개질 수 있다. 아래 §1.4 참고.)
- ⚠️ **현재 레포에는 `clean_af3_outputs.py`만 구현돼 있다.** `af3_convert.py`,
  `af3_extract_features.py`, `cif_distance.py`는 아직 작성 전이라, 이 문서의 §2·§4·§5에 적힌
  옵션은 **앞으로 만들 때 맞출 목표 사양(합의안)**이다. 스크립트를 실제로 만든 뒤에는 반드시
  각 스크립트의 `--help` 출력과 이 문서를 서로 맞춰야 한다(다르면 둘 중 하나를 고친다).

## 0. 먼저: 출력 폴더는 어떻게 생겼나

AF3 한 번 실행(한 "job") = 폴더 하나. 복합체 하나당 우리는 **15 seed × 5 model = 75개 도킹 모델**을
만든다. "seed(시드)"는 난수 초기값으로, **같은 seed = 같은 결과**가 나오므로 재현성을 위해 seed를
직접 고정한다. seed 하나당 model(=sample) 5개가 나오니 15×5=75개가 된다.

폴더 구조는 대략 이렇다. 단, 아래는 **DeepMind 공식 로컬 AF3** 기준의 한 예시이고, **이름·하위
폴더 구조는 AF3 버전과 실행 환경(로컬 vs AlphaFold Server 웹 다운로드 zip)에 따라 다를 수 있다.**
처음 받은 결과는 실제 `ls`로 한 번 훑어 구조를 확인하자.

```
<job_name>/
├── <job_name>_model.cif                      # 1등(top-ranking) 구조
├── <job_name>_summary_confidences.json       # 1등의 요약 신뢰도
├── <job_name>_confidences.json               # 1등의 상세 신뢰도 (= 우리가 말하는 full_data)
├── ranking_scores.csv                        # 75개 모델의 순위 점수표
├── seed-1_sample-0/                           # seed 1, model 0
│   ├── ..._seed-1_sample-0_model.cif
│   ├── ..._seed-1_sample-0_summary_confidences.json
│   └── ..._seed-1_sample-0_confidences.json
├── seed-1_sample-1/
│   └── ...
├── ...                                        # seed × sample 조합마다 하나씩
├── msas/                                      # 멀티서열정렬 중간 산출물 (§3)
└── template/                                  # 구조 템플릿 중간 산출물 (§3)
```

> 파일 이름에 대한 주의 — 같은 정보를 가진 파일이 환경에 따라 **이름이 다를 수 있다.**
> - **로컬에서 직접 돌린 AF3**(DeepMind 공식 코드): 상세 파일이 `*_confidences.json`,
>   요약 파일이 `*_summary_confidences.json`.
> - **AlphaFold Server(웹)**나 우리 내부 관례에서는 같은 상세 파일을 흔히 **`*_full_data_#.json`**,
>   요약을 **`*_summary_confidences_#.json`** 처럼 `#`(모델 번호)를 붙여 부르기도 한다.
>
> 이 문서와 우리 스크립트는 **`*_full_data*.json` / `*_summary_confidences*.json` / `*_confidences.json`**
> 같은 표현을 쓰지만, **들어 있는 JSON 키(key)는 양쪽이 사실상 동일**하다. 헷갈리면
> "상세 = full_data = confidences", "요약 = summary_confidences"로 기억하면 된다.
> 스크립트는 어느 쪽 이름이든 패턴으로 찾도록 만드는 것을 목표로 한다.
> **⚠️ 우리 실제 멘토 데이터의 정확한 파일명은 받은 데이터로 직접 확인이 필요하다.**

## 1. 출력 파일 하나씩

### 1.1 `*_model.cif` — 구조 좌표 (3D 모델 그 자체)

이게 "도킹 결과 구조"다. 항원과 항체가 어떤 모양으로 어떻게 붙었는지를 담은 **원자 좌표 파일**이다.

- **cif가 뭔가?** CIF = *Crystallographic Information File*(결정학 정보 파일).
  현대 단백질 구조의 표준 텍스트 포맷이다. 옛날부터 쓰던 `.pdb` 포맷의 후속/확장판이라고 보면 된다
  (정식 명칭은 mmCIF). 안에는 원자 종류·좌표(x,y,z)·체인 기호·잔기 번호 같은 게 줄줄이 들어 있다.
  텍스트라서 그냥 열어볼 수도 있지만, 사람이 눈으로 읽으려고 만든 건 아니다.
- **"잔기(residue)"** = 단백질을 이루는 아미노산 한 개 단위. 단백질은 아미노산이 사슬로 이어진 것이라,
  잔기 번호 1, 2, 3...으로 위치를 센다.

**PyMOL에서 여는 법.** PyMOL은 단백질 구조를 3D로 돌려보는 뷰어다(오픈소스 빌드 또는 유료 버전).

방법 A — 앱에서 직접:
1. PyMOL 실행.
2. 메뉴 `File > Open...` 에서 `.cif` 파일 선택. 끝. 마우스로 돌려보면 항원-항체가 붙은 모양이 보인다.

방법 B — PyMOL 명령줄(아래쪽 입력창)에서:
```text
load /절대/경로/<job_name>_model.cif, mymodel
hide everything
show cartoon
util.cbc          # chain마다 색을 다르게 (color by chain)
```
- `cartoon`은 단백질의 큰 골격(나선·병풍)을 만화처럼 단순화해 보여주는 표현이다.
- `util.cbc`로 체인별로 색을 칠하면 chain A(항원)와 chain B(항체)가 한눈에 구분된다.

> 참고: 75개 모델 중 어느 게 좋은지는 좌표만 봐선 모른다. 신뢰도 점수(아래)와 우리 ML 피처가 그걸 판단한다.

### 1.2 `*_summary_confidences*.json` — 요약 신뢰도 (모델당 스칼라 몇 개)

JSON(제이슨)은 `키: 값` 형태의 텍스트 데이터 파일이다. 이 요약 파일에는 모델 전체를 한두 숫자로
압축한 **스칼라(scalar, 값 하나짜리 숫자)** 들이 들어 있다. 주요 키(DeepMind 공식 output 문서 기준,
버전에 따라 추가/변경될 수 있음):

- `iptm` — *interface pTM*. 서로 다른 체인 **사이(계면)** 의 정렬 신뢰도. 0~1, 높을수록 좋음.
  **우리 프로젝트의 출발점이자 비교 대상(baseline)** 이다. AF3는 이 `iptm`을 전역(global) 기준으로
  계산해서, 계면의 **국소(local)** 기하·물리화학 상보성을 못 잡는다 — 그래서 좋은 포즈가 낮은 iptm에
  묻히는 false-negative가 생긴다. 우리는 그걸 ML로 구제(rescue)하려는 것.
- `ptm` — *predicted TM-score*. 구조 **전체**의 정렬 신뢰도(체인 안쪽 포함).
- `ranking_score` — AF3가 모델들을 줄 세울 때 쓰는 종합 점수.
- `chain_pair_iptm` — 체인 쌍별 iptm 행렬(예: A-B 쌍의 iptm). 우리는 A↔B(항원-항체) 칸이 핵심.
- `chain_pair_pae_min` — 체인 쌍별 PAE 최소값. (PAE는 §1.3에서 설명.)
- `chain_ptm`, `chain_iptm` — 체인별 ptm/iptm.
- `has_clash`, `fraction_disordered` — 충돌 여부, 흐트러진(무질서) 영역 비율 같은 품질 플래그.

> 이 파일은 "이미 요약된" 값이라 ML 피처로 직접 쓰기엔 거칠다. 진짜 재료는 다음 상세 파일에 있다.

### 1.3 `*_full_data*.json` (= `*_confidences.json`) — 상세 신뢰도 (행렬·배열; 우리 피처의 원천)

여기서 우리 ML 계면 피처를 뽑는다. 주요 키(공식 output 문서 기준; 버전에 따라 다를 수 있음):

- **`atom_plddts`** — **원자별 pLDDT** 배열. 길이 = 원자 개수.
  pLDDT(*predicted Local Distance Difference Test*)는 **그 위치를 모델이 얼마나 확신하는지**를
  0~100으로 나타낸 국소 신뢰도다(높을수록 확신). 직관: cryo-EM(저온전자현미경) 구조에서 B-factor로
  부위별 신뢰도를 색칠하듯, pLDDT로 구조를 색칠하면 "잘 맞춘 부위 vs 흐릿한 부위"가 보인다.
  계면(항원-항체가 닿는 부위)의 pLDDT가 높으면 그 접촉을 믿을 만하다는 신호.
- **`contact_probs`** — **잔기(토큰) 접촉 확률 행렬**. 크기 = `[토큰수 × 토큰수]`.
  `(i, j)` 칸 = 토큰 i와 j가 닿아 있을(가까울) 확률.
  **대칭(symmetric)** 이다 — "i가 j에 닿음"과 "j가 i에 닿음"은 같은 사건이라 `(i,j)=(j,i)`.
  우리는 이 행렬에서 **A행 × B열**(항원-항체 교차 부분)만 떼어내 계면 접촉을 본다.
  > ⚠️ **주의:** AF3가 `contact_probs`를 계산할 때 쓰는 "접촉" 정의(대표 원자 간 약 8 Å 이내)와,
  > 우리가 §5에서 그래프화에 쓰는 컷오프(heavy-atom 5.0 Å)는 **서로 다른 기준**이다. 같은 단어
  > "접촉"이라도 거리 기준이 다르니 혼동하지 말 것.
- **`pae`** — **PAE(Predicted Aligned Error) 행렬**. 크기 = `[토큰수 × 토큰수]`, 단위는 Å(옹스트롬).
  `(i, j)` 칸 = "**토큰 i의 좌표계(frame)에 구조를 맞춰 정렬**했을 때, **토큰 j**의 위치가
  실제와 얼마나 어긋날 것으로 예측되는지"의 오차. **작을수록 좋다**(두 토큰의 상대 위치를 확신).
  - **왜 비대칭(asymmetric)인가? — A→B와 B→A가 다르다.** 핵심은 "**i에 시점을 고정하고 j를 본다**"는
    비대칭적 정의 때문이다. 비유하자면, 내가 **건물 A에 서서** 멀리 있는 **건물 B**가 어디 있을지
    가늠하는 오차와, **건물 B에 서서** A를 가늠하는 오차는 다를 수 있다. 한쪽(예: 항원 코어)은 단단히
    고정돼 있어 거기 서서 보면 상대가 잘 보이지만, 반대쪽(예: 유연한 항체 루프)에 서서 보면 시점 자체가
    흔들려 상대 위치가 더 부정확해진다. 그래서 `(i,j) ≠ (j,i)`이고, **A→B(항원 기준 항체 오차)와
    B→A(항체 기준 항원 오차)를 둘 다 봐야** 계면 신뢰도를 제대로 평가한다. 우리 피처 추출도 두 방향을
    따로 계산한다(§4).
- **`token_chain_ids`** — 토큰(≈잔기)마다 어느 체인 소속인지(`"A"`, `"B"`, ...)를 적은 배열.
  이게 있어야 행렬에서 "A에 속한 토큰 = 항원", "B = 항체"를 골라낼 수 있다.
- **`atom_chain_ids`** — 원자마다의 체인 기호(원자 단위 버전). `atom_plddts`와 짝지어 쓴다.

> **토큰(token) vs 잔기(residue)** — AF3 내부에서는 입력 단위를 "토큰"이라 부른다. 단백질 잔기는
> 보통 토큰 1개에 대응하므로, 실무에선 "토큰 ≈ 잔기"로 봐도 무방하다(리간드·변형 잔기 등은 예외).
> 잔기 번호는 별도 키(`token_res_ids` 등)가 버전에 따라 있을 수도 있으나 공식 핵심 키 목록에는
> 명시돼 있지 않으니, 기본적으로는 `token_chain_ids` + 토큰 순서로 위치를 짚는다.

### 1.4 체인이 여러 개인 경우 (Fab/scFv 주의)

AF3는 전체 IgG(항체 한 통째) 포맷은 잘 못 받아서, 항체를 **Fab**(항원결합 절편) 또는 **scFv**(단일사슬
가변절편) 형태로 넣는 게 일반적이다.

- **Fab**으로 넣으면 항체가 **중쇄 절편 + 경쇄 = 체인 2개**가 될 수 있다. 그러면 chain B 하나가 아니라
  B, C처럼 나뉜다.
- **scFv**는 보통 단일 사슬이라 체인 1개로 들어간다.

즉 항상 "A=항원, B=항체"가 깔끔하게 1:1은 아닐 수 있다. 계면 피처를 뽑을 때 **항원 체인 집합 vs 항체
체인 집합**을 명시적으로 지정하는 이유다(§4의 `--antigen`/`--antibody` 옵션).

## 2. cif → pdb 변환 (`scripts/af3_convert.py`) — *예정 스크립트*

> ⚠️ 이 스크립트는 **아직 레포에 없다.** 아래 옵션은 작성 시 맞출 목표 사양이다. 실제로 만든 뒤
> `--help`로 옵션을 다시 확인하라.

### 왜/언제 필요한가
`.cif`는 최신 표준이고 PyMOL·ChimeraX 같은 최신 뷰어는 잘 읽는다. 그런데 **오래된 도구나 일부
파이썬 라이브러리·도킹 프로그램은 `.pdb`만 받거나 `.pdb`에서 더 안정적**이다. 그래서 후속 분석
도구가 `.pdb`를 요구할 때 변환이 필요하다. (반대로 최신 뷰어만 쓸 거면 변환 없이 `.cif` 그대로 둬도 된다.)

> 주의: `.pdb`는 옛 포맷이라 **체인 기호가 1글자**, 원자 수가 아주 많은 거대 복합체는 잘릴 수 있다.
> 우리 항원-항체 복합체는 보통 문제없지만, 변환 후 PyMOL로 한 번 열어 확인하는 습관을 들이자.

### 사용법 (예정 사양)
```bash
# 단일 파일 변환: 같은 폴더에 같은 이름의 .pdb 생성
python scripts/af3_convert.py path/to/<job>_model.cif

# 출력 경로 지정
python scripts/af3_convert.py path/to/<job>_model.cif -o path/to/out.pdb

# 폴더 통째로 (하위까지 재귀) 모든 .cif 변환
python scripts/af3_convert.py path/to/job_folder/ --recursive
```
실행 후 같은 위치(또는 `-o` 경로)에 `.pdb`가 생겼는지 `ls`로 확인한다.

> 옵션 이름·동작 세부는 스크립트 상단 도움말로 항상 재확인:
> ```bash
> python scripts/af3_convert.py --help
> ```

## 3. `msas/`, `template/` 폴더 — 왜 생기고, 왜 걸리나 (`scripts/clean_af3_outputs.py`)

> ✅ 이 스크립트는 **레포에 이미 구현돼 있다.** 아래 사용법은 실제 구현(`--help` 출력)과 일치한다.

### 왜 생기나
AF3는 구조를 예측하기 전에 두 가지 준비 자료를 만든다(로컬 AF3의 data-pipeline 산출물 기준).
- **`msas/`** — *Multiple Sequence Alignment*(다중 서열 정렬). 입력 단백질과 **진화적으로 비슷한
  서열들을 데이터베이스에서 긁어 정렬**한 것. 모델이 "이 단백질이 어떻게 접히는지"의 진화적 단서를
  얻는 재료다. 파일이 많고 용량이 크다.
- **`template/`** — 입력과 닮은 **기존 PDB 구조 템플릿**들. 비슷한 구조를 참고하라고 넣는 자료.

이것들은 **예측을 위한 중간 산출물**이지, 우리가 분석할 결과물이 아니다.
> ⚠️ 서버(AlphaFold Server)에서 받은 결과 zip에는 이 폴더가 **없거나 이름이 다를 수 있다.**
> 그래서 이 스크립트는 기본으로 `msas`, `msa`, `template`, `templates` 네 가지 이름을 찾고, 다른
> 이름이면 `--names`로 지정하게 돼 있다(아래).

### 왜 후속 분석에서 걸리나
우리 피처 추출 스크립트(§4)는 출력 폴더를 **재귀적으로 훑으며 `*_full_data*.json` / `*_model.cif`를
찾는다.** 그런데 `msas/`·`template/` 안에도 `.json`·`.cif` 비슷한 파일이 섞여 있으면, 검색에 끼어
**파싱 에러를 내거나 엉뚱한 파일을 집어 들 수 있다.** 게다가 용량이 커서 서버↔로컬 전송(`scp`)도 느려진다.
그래서 분석 전에 이 폴더들을 **재귀적으로 삭제**하는 게 유리하다.

### 안전하게 지우기 — 이 스크립트는 **기본이 예행 연습(DRY-RUN)** 이다
`rm -rf`를 직접 치면 오타 한 번에 엉뚱한 걸 날릴 수 있으니, 전용 스크립트를 쓴다.
**이 스크립트의 핵심 안전 설계:**

- **아무 플래그 없이 실행하면 = DRY-RUN.** 즉 "무엇이 지워질지"만 목록으로 보여주고 **실제로는
  아무것도 지우지 않는다.** (그래서 먼저 그냥 실행해 목록을 눈으로 확인하는 게 1단계다.)
- **실제로 지우려면 반드시 `--apply` 플래그를 붙여야 한다.** `--apply`가 없으면 절대 삭제되지 않는다.
- (참고: 이 스크립트에는 `--dry-run` 같은 별도 플래그가 없다 — DRY-RUN이 *기본값*이기 때문.)

```bash
# 1단계 (안전 기본값): 플래그 없이 실행 → 무엇이 지워질지 목록만 출력. 실제 삭제 없음.
python scripts/clean_af3_outputs.py path/to/af3_outputs/

# 2단계: 목록을 눈으로 확인해 이상 없으면, --apply 를 붙여 실제 삭제
python scripts/clean_af3_outputs.py path/to/af3_outputs/ --apply

# (선택) 지울 폴더 이름을 직접 지정하고 싶을 때
python scripts/clean_af3_outputs.py path/to/af3_outputs/ --names msas template --apply
```
- 기준 폴더(`base_dir`)는 **위치 인자**로 첫 번째에 준다(이 폴더 아래만 건드린다).
- 기본 삭제 대상 이름: `msas`, `msa`, `template`, `templates` (대소문자 무시).
- 안전장치: 삭제 대상이 `base_dir` **바깥**을 가리키면 거부하고, 심볼릭 링크는 따라 들어가지 않는다.
- `model.cif`·`*_full_data*.json`·`*_summary_confidences*.json` 같은 **진짜 결과물은 건드리지 않는다.**
  (대상은 폴더 *이름*으로만 고르기 때문.)
- 옵션 재확인:
  ```bash
  python scripts/clean_af3_outputs.py --help
  ```

> ⚠️ 이 스크립트는 폴더를 **통째로(rmtree)** 지우며, 한 번 지우면 복구할 수 없다. 또한 실제
> AF3 데이터로 검증되지 않았으니, 처음에는 **사본·테스트 폴더**에서 `--apply`를 한 번 시험해 보고
> 실제 데이터에 쓰는 것이 안전하다.

> 습관: 새 AF3 결과를 받으면 **(1) 플래그 없이 실행해 미리보기 → (2) 목록 확인 후 `--apply`로
> 실제 삭제 → (3) 피처 추출** 순서로 간다.

## 4. 계면 피처 추출 → CSV (`scripts/af3_extract_features.py`) — *예정 스크립트*

> ⚠️ 이 스크립트는 **아직 레포에 없다.** 아래 옵션·CSV 컬럼명은 작성 시 맞출 목표 사양이다.
> 실제로 만든 뒤 `--help`와 출력 헤더로 다시 확인하라.

이게 이 문서의 핵심 단계다. `*_full_data*.json`에서 **항원-항체 계면**의 숫자 피처를 뽑아
모델 한 개 = CSV 한 행으로 정리한다. 그 CSV가 우리 ML 모델의 입력이 된다.

### 무엇을 뽑나 (피처의 정의)
계면 = **A(항원) 토큰들 × B(항체) 토큰들의 교차 블록**. 행렬에서 A행·B열만 떼어낸 직사각형 부분이다.

1. **계면 contact top-N 평균** — `contact_probs`의 A↔B 교차 블록에서 **접촉 확률이 큰 상위 N개 값의
   평균.** "가장 확실한 접촉 N개가 평균적으로 얼마나 강한가" = 계면이 단단히 붙었는지의 신호.
   (대칭 행렬이므로 A행×B열 한 방향만 봐도 충분.)
2. **PAE 방향별 최소값 top-N** — `pae`의 A↔B 교차 블록에서 **가장 작은(=가장 확신하는) 상위 N개의 평균.**
   PAE는 **비대칭**이라 두 방향을 따로 뽑는다:
   - **A→B**: 항원 토큰 기준으로 본 항체 토큰의 오차 블록.
   - **B→A**: 항체 토큰 기준으로 본 항원 토큰의 오차 블록.
   둘 다 "작을수록 좋은" 양이므로 **최소값**을 모은다. 두 방향이 다를 수 있어 **둘 다** 피처로 쓴다(§1.3).
3. **계면 pLDDT** — 계면에 닿는 잔기들의 `atom_plddts` 평균(또는 계면 잔기 pLDDT 평균). 계면 부위를
   모델이 얼마나 확신하는지.

> N(top-N의 N)·계면 판정 방식 등은 옵션으로 조절한다(아래). 기본값은 스크립트 `--help`로 확인.

### 사용법 (예정 사양)
```bash
# 폴더 안 모든 모델을 재귀 탐색해 한 CSV로 모으기
python scripts/af3_extract_features.py path/to/af3_outputs/ \
  -o data/features.csv \
  --antigen A \
  --antibody B \
  --top-n 10

# 항체가 Fab이라 체인이 2개(B,C)인 경우: 항체 체인을 여러 개 지정
python scripts/af3_extract_features.py path/to/af3_outputs/ \
  -o data/features.csv \
  --antigen A \
  --antibody B,C \
  --top-n 10
```
- `--antigen` / `--antibody` — 어느 체인이 항원/항체인지 지정(기본 관례 A=항원, B=항체).
  Fab/scFv로 체인이 쪼개지면 여기서 명시(§1.4).
- `--top-n` — contact·PAE에서 상위 몇 개를 평균낼지(N).
- `-o` — 출력 CSV 경로. (`data/`는 `.gitignore`에 들어 있어 커밋되지 않는다. 폴더가 없으면
  `mkdir -p data` 로 먼저 만든다.)
- 입력 폴더를 주면 **하위까지 재귀**로 `*_full_data*.json`을 찾는다 → 그래서 §3에서 `msas/`·`template/`를
  먼저 지워두는 게 중요하다.

> 항상 재확인:
> ```bash
> python scripts/af3_extract_features.py --help
> ```

### 출력 CSV 컬럼 의미 (예정 사양)
모델 1개 = 1행. 대략 이런 컬럼을 목표로 한다(정확한 이름은 구현 후 스크립트 출력 헤더를 확인):

| 컬럼 | 의미 |
|---|---|
| `model_id` / `path` | 어느 모델(어느 폴더/파일)에서 나온 값인지 식별자 |
| `pdb_id` | 어느 복합체(PDB) 소속인지 — **GroupKFold에서 PDB 단위로 묶어 누수 차단**할 때 쓰는 그룹 키 |
| `seed`, `sample` | 그 모델의 seed·model 번호 |
| `iptm` | 요약 파일의 iptm — **비교 baseline**으로 같이 적어둠 |
| `ptm`, `ranking_score` | 요약 스칼라(참고용) |
| `contact_topN_mean` | 계면 contact 확률 상위 N개 평균 (피처 1) |
| `pae_AtoB_min_topN` | A→B 방향 PAE 최소 상위 N개 평균 (피처 2-방향1) |
| `pae_BtoA_min_topN` | B→A 방향 PAE 최소 상위 N개 평균 (피처 2-방향2) |
| `interface_plddt_mean` | 계면 잔기 pLDDT 평균 (피처 3) |

> 라벨(DockQ·성공 여부 등)은 이 CSV에 합치거나 따로 둔다. 우리 성공 기준은 **DockQ ≥ 0.23**.
> CSV가 나오면 `pandas`로 열어 행 수(=모델 수)와 결측치(NaN)를 한 번 점검하는 습관을 들이자.

## 5. cif/pdb로 추가 분석 — 잔기간 거리 (`scripts/cif_distance.py`) — *예정 스크립트*

> ⚠️ 이 스크립트는 **아직 레포에 없다.** 아래 옵션은 작성 시 맞출 목표 사양이다.
> 실제로 만든 뒤 `--help`로 확인하라.

JSON 행렬 말고 **실제 3D 좌표**에서 직접 재고 싶을 때가 있다. 대표적으로 **두 잔기가 실제로 몇 Å
떨어져 있는지**(계면 접촉 정의·검증·시각화용)다. 이건 구조 파일(`.cif`/`.pdb`)에서 좌표를 읽어 계산한다.

### 사용법 (예정 사양)
```bash
# 한 구조에서 항원(A)–항체(B) 사이 가까운 잔기쌍을 거리순으로
python scripts/cif_distance.py path/to/<job>_model.cif \
  --chain1 A --chain2 B \
  --cutoff 5.0 \
  -o data/contacts.csv

# 특정 두 잔기 사이 거리만
python scripts/cif_distance.py path/to/<job>_model.cif \
  --res1 A:45 --res2 B:101
```
- `--chain1`/`--chain2` — 거리 잴 두 체인(항원 A, 항체 B).
- `--cutoff` — 이 거리(Å) 이내로 닿는 잔기쌍만 "접촉"으로 출력. 우리 **그래프화 기준이 heavy-atom 5.0 Å**라
  `--cutoff 5.0`이 기본 감각. (heavy-atom = 수소를 뺀 무거운 원자 기준 거리.)
  > ⚠️ 이 5.0 Å는 **우리 그래프화 컷오프**이고, §1.3의 `contact_probs`가 쓰는 약 8 Å 정의와는 **다른
  > 기준**이다. 둘을 같은 "접촉"으로 섞어 해석하지 말 것.
- `--res1`/`--res2` — `체인:잔기번호` 형식으로 특정 두 잔기 거리만.
- `-o` — 결과 CSV(접촉 잔기쌍과 거리). 안 주면 화면 출력.

> 항상 재확인:
> ```bash
> python scripts/cif_distance.py --help
> ```

> 이 거리 분석은 §4의 contact_probs(모델이 "예측"한 접촉 확률)와 비교하는 **검증** 용도로도 좋다.
> 예: PAE/contact가 가깝다고 한 잔기쌍이 실제 좌표상으로도 5 Å 안에 들어오는지.
