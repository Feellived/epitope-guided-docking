# 03. 연구실 리눅스 서버: ssh 접속 · 파일 전송 · 장시간 세션 유지

> ⚠️ **이 문서는 2026년 6월 시점 기준이며 이후 갱신하지 않았다.**
> 현재 파이프라인은 `pipeline/` 에 있다. 배경은 `legacy_af3/README.md` 참조.

이 문서는 연구실 리눅스 서버에 **처음 접속**해서, **파일을 주고받고**, **오래 걸리는 작업을
끊김 없이 돌리는** 가장 기초적인 흐름을 정리한 것이다. 주피터/코랩만 써 봤고 터미널은 거의
처음이라는 가정으로, "무엇을 / 왜 / 어떻게"를 단계별로 짚는다. 한 번씩 직접 손으로 쳐 보는 게
목적이다.

> 보안 주의: 이 문서에는 실제 서버 주소·계정·비밀번호를 **절대 쓰지 않는다.** 아래 명령에서
> `<YOUR_SERVER_IP>`(서버 주소), `<PORT>`(접속 포트 번호), `<USER>`(내 계정 이름)는 멘토에게
> 받은 실제 값으로 **머릿속/메모에서만** 바꿔 친다. 메모도 깃에 올라가는 폴더에는 두지 않는다.

> 환경 주의: 아래 명령은 **내 맥(로컬)**에서 치는 것과 **서버 안**에서 치는 것이 섞여 있다.
> 어디서 치는지 각 단락에 표시해 두었다. 또한 `tmux`·`rsync`·`nvidia-smi`·`ssh-copy-id` 등은
> 서버(또는 내 맥)에 설치돼 있어야 동작한다. 없으면 "command not found"가 뜨는데, 그건 고장이
> 아니라 그 도구가 안 깔린 것뿐이다 — 대안(아래 각 절 참고)을 쓰거나 멘토에게 문의한다.

용어 빠른 풀이:
- **서버(server):** 연구실에 있는, 항상 켜져 있고 GPU가 달린 강력한 리눅스 컴퓨터. AF3 같은
  무거운 계산을 여기서 돌린다.
- **로컬(local):** 지금 내 손에 있는 맥북. 여기서 명령을 쳐서 서버에 접속한다.
- **터미널(terminal):** 명령어를 글자로 입력하는 검은 창. 맥은 기본 "터미널" 앱 또는 VSCode
  안의 통합 터미널을 쓰면 된다(VSCode 설정은 `docs/00_VSCode_파이썬_워크플로.md` 참고 — 이 문서는
  추후 작성 예정).

## 1. ssh로 서버에 접속하기  (내 맥에서 실행)

### 무엇 / 왜

`ssh`(Secure Shell)는 **내 맥에서 멀리 있는 서버에 안전하게 로그인**해서, 마치 그 서버 앞에
앉아 있는 것처럼 명령을 치게 해 주는 도구다. 접속하면 내 터미널 입력이 전부 서버로 전달된다.
"Secure"는 통신이 암호화되어 중간에서 엿볼 수 없다는 뜻이다. (맥에는 ssh가 기본 설치돼 있다.)

### 어떻게

맥의 터미널에서 아래 형태로 친다.

```bash
ssh -p <PORT> <USER>@<YOUR_SERVER_IP>
```

뜻을 하나씩 보면:
- `ssh` — 접속 프로그램.
- `-p <PORT>` — 접속할 **포트 번호**(소문자 `p`). 포트는 "서버로 들어가는 문 번호" 같은 것.
  기본값(22)을 쓰는 서버라면 `-p` 자체를 생략할 수 있지만, 연구실 서버는 다른 번호를 쓰는
  경우도 있으니 멘토가 알려준 번호를 넣는다. (포트가 기본 22인지 아닌지는 서버마다 다르다.)
- `<USER>@<YOUR_SERVER_IP>` — `내계정이름@서버주소` 형식. 서버 주소는 숫자 IP(예: `203.0.113.x`
  형태)일 수도, 도메인 이름일 수도 있다.

예시(값은 전부 가짜 placeholder):

```bash
ssh -p 22000 myid@<YOUR_SERVER_IP>
```

### 비밀번호 방식 vs SSH 키 방식

접속할 때 "내가 맞다"는 걸 증명하는 방법이 두 가지다. **어느 방식을 허용하는지는 서버 정책에
따라 다르다**(키만 받고 비밀번호는 막아 둔 서버도 있다). 안 되면 멘토에게 확인한다.

1. **비밀번호 방식** — 접속할 때마다 비밀번호를 입력한다. 가장 간단하고, 처음엔 보통 이 방식
   으로 시작한다. (참고: 비밀번호를 칠 때 화면에 글자나 `*`가 **전혀 안 보이는 게 정상**이다.
   안 보여도 입력은 되고 있으니 그대로 치고 Enter.)

2. **SSH 키 방식** — 내 맥에 **열쇠 한 쌍**(개인키 + 공개키)을 만들어 두고, 공개키를 서버에
   등록해 두면 그 다음부터는 **비밀번호 없이** 접속된다. 매번 비밀번호를 안 쳐도 되고 더 안전
   해서 익숙해지면 권장된다. (열쇠 비유: 개인키 = 내가 가진 진짜 열쇠, 공개키 = 서버 문에 달린
   자물쇠. 자물쇠는 공개돼도 되지만 열쇠는 절대 남에게 주지 않는다. 개인키 파일
   `~/.ssh/id_ed25519`는 누구에게도 보내거나 깃에 올리지 않는다.)

SSH 키를 만들고 등록하는 최소 절차(처음 한 번만, **내 맥에서 실행**):

```bash
# 1) 내 맥에서 키 한 쌍 생성 (질문이 나오면 일단 Enter로 기본값 사용해도 됨)
ssh-keygen -t ed25519

# 2) 공개키를 서버에 등록 (이때 한 번은 비밀번호를 물어봄)
ssh-copy-id -p <PORT> <USER>@<YOUR_SERVER_IP>

# 3) 이후엔 비밀번호 없이 접속되는지 확인
ssh -p <PORT> <USER>@<YOUR_SERVER_IP>
```

`ssh-copy-id`가 없거나(맥에는 보통 있음), 서버가 키 인증을 막아 등록이 안 되면 비밀번호 방식
으로 계속 써도 된다. 키 등록은 나중에 멘토에게 물어 천천히 해도 된다.

### 처음 접속 시 나오는 fingerprint(지문) 확인

**처음** 어떤 서버에 접속하면 아래 비슷한 메시지가 한 번 뜬다.

```text
The authenticity of host '[<YOUR_SERVER_IP>]:<PORT>' can't be established.
ED25519 key fingerprint is SHA256:xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx.
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

- **이게 뭐냐:** "이 서버가 진짜 그 서버가 맞는지 아직 모른다"는 안내다. `fingerprint`(지문)는
  서버를 식별하는 고유 문자열이다.
- **어떻게:** 멘토가 알려준 서버가 맞다면 `yes`를 입력하고 Enter. 그러면 그 서버의 지문이
  내 맥의 `~/.ssh/known_hosts`("이미 믿기로 한 서버들" 목록 파일)에 저장되고, **다음부터는 이
  질문이 안 뜬다.**
- **주의:** 평소 잘 접속하던 서버인데 어느 날 갑자기 "지문이 바뀌었다(WARNING: REMOTE HOST
  IDENTIFICATION HAS CHANGED)"는 경고가 뜨면, 그냥 넘기지 말고 멘토에게 확인한다. 서버를 새로
  설치했을 수도 있지만, 드물게 보안 문제 신호일 수도 있다. (서버가 정말 재설치된 거라면, 멘토
  확인 후 안내대로 옛 지문을 지운다 — 보통 `ssh-keygen -R "[<YOUR_SERVER_IP>]:<PORT>"`.)

접속을 끝낼 때는 **서버 안에서** 다음을 친다(또는 `Ctrl-d`):

```bash
exit
```

## 2. scp로 파일 주고받기  (내 맥에서 실행)

### 무엇 / 왜

`scp`(Secure Copy)는 **ssh와 같은 안전한 통로로 파일을 복사**하는 도구다. 내 맥의 파일을
서버로 올리거나(업로드), 서버의 결과 파일을 내 맥으로 내려받을(다운로드) 때 쓴다. **명령은
서버가 아니라 내 맥에서** 친다.

> 핵심 함정: ssh는 포트 옵션이 **소문자 `-p`**, scp는 **대문자 `-P`**다. 헷갈리기 쉬우니
> "scp는 P가 크다"로 외운다.

> 버전 참고: 요즘 맥/리눅스의 scp는 내부적으로 SFTP라는 프로토콜로 동작한다(예전 방식과 약간
> 다름). 아래 예시는 버전에 상관없이 잘 되지만, 폴더 복사 시 "이미 같은 이름의 폴더가 있는가"에
> 따라 안에 한 겹 더 들어가는 등 미묘한 차이가 날 수 있다. 받은 뒤 `ls`로 어디에 들어갔는지
> 한 번 확인하는 습관을 들인다.

### 로컬 → 서버 (올리기)

```bash
scp -P <PORT> 로컬파일 <USER>@<YOUR_SERVER_IP>:원격경로
```

예시: 내 맥의 `input.fasta`를 서버 홈 디렉토리로 올리기.

```bash
scp -P <PORT> input.fasta <USER>@<YOUR_SERVER_IP>:~/
```

- `~` 는 "내 홈 디렉토리"를 뜻한다(예: `/home/<USER>`).
- 콜론(`:`) **뒤가 서버 안의 경로**다. 콜론을 빠뜨리면 그냥 로컬에서 로컬로 복사돼 버리니 주의.

### 서버 → 로컬 (가져오기)

방향만 반대다. 즉 **서버 경로를 앞에, 로컬 경로를 뒤에** 쓴다.

```bash
scp -P <PORT> <USER>@<YOUR_SERVER_IP>:원격파일 로컬경로
```

예시: 서버의 결과 파일 하나를 지금 폴더(`.`)로 내려받기.

```bash
scp -P <PORT> <USER>@<YOUR_SERVER_IP>:~/results/summary_confidences_0.json .
```

`.` 은 "지금 내가 있는 폴더"를 뜻한다.

### 폴더째로 받기: AF3 결과 폴더 (`-r`)

파일 하나가 아니라 **폴더 전체**를 복사할 때는 `-r`(recursive, 하위까지 전부)을 붙인다.
AF3 결과는 보통 폴더 하나에 구조 `.cif`와 여러 `.json`이 들어 있으므로 `-r`로 통째로 받는다.

```bash
scp -r -P <PORT> <USER>@<YOUR_SERVER_IP>:~/af3_runs/complex01 ./complex01
```

> 팁: AF3 출력 폴더 안에는 `msas/`, `template/` 같은 보조 폴더가 같이 들어 있어 용량이 크고
> 후속 분석에서 거치적거린다. 받기 전에 **서버에서 먼저** 지워 두면 전송이 빠르다. 손으로
> `rm -rf` 하지 말고 검증된 스크립트를 쓴다(§4 참고). 예행 연습이 기본이라 안전하다:
>
> ```bash
> # (서버 안에서) 먼저 무엇이 지워질지 목록만 본다 — 실제 삭제 안 함
> python scripts/clean_af3_outputs.py ~/af3_runs/complex01
> # 목록이 맞으면 그때 --apply 를 붙여 실제 삭제
> python scripts/clean_af3_outputs.py ~/af3_runs/complex01 --apply
> ```
>
> AF3 출력 처리 전반은 `docs/02_AF3_출력_처리.md`(추후 작성 예정) 참고.

### 대안: rsync (큰 폴더·재전송에 유리)

`rsync`는 scp와 비슷하지만 **이미 받은 파일은 건너뛰고 바뀐 부분만** 다시 받아서, 큰 폴더를
여러 번 동기화할 때 훨씬 빠르고 중간에 끊겨도 이어받기 쉽다. ssh 포트를 함께 지정하는 형태만
살짝 다르다. (rsync는 내 맥과 서버 **양쪽**에 설치돼 있어야 한다. 맥에는 보통 있다.)

```bash
rsync -avz -e "ssh -p <PORT>" <USER>@<YOUR_SERVER_IP>:~/af3_runs/complex01 ./
```

- `-avz`는 대략 "하위까지 보존하며 압축 전송"이라는 옵션 묶음. 지금은 그대로 따라 쓰면 된다.
- 위 명령은 `complex01` 폴더를 현재 폴더 안에 `./complex01`로 받는다.
- **rsync 함정(끝의 `/`):** 원본 경로 끝에 슬래시가 있고 없고에 따라 동작이 달라진다.
  `.../complex01`(슬래시 없음)은 폴더 **자체**를 복사(→ `./complex01`), `.../complex01/`(슬래시
  있음)은 폴더 **안의 내용물**만 복사한다. 헷갈리면 일단 슬래시 없이 쓰고 `ls`로 확인한다.

## 3. tmux로 끊겨도 죽지 않는 세션 만들기  (서버 안에서 실행)

### 무엇 / 왜

ssh로 접속한 채 무거운 작업(예: AF3 실행, 모델 학습)을 돌리는 도중 **노트북을 닫거나 와이파이가
끊기면, 그 작업도 같이 죽어 버린다.** 몇 시간짜리 작업이 날아가면 치명적이다.

`tmux`(terminal multiplexer)는 서버 안에 **떼었다 붙였다 할 수 있는 가상 터미널 세션**을 만들어
준다. 세션 안에서 작업을 시작해 두고 "분리(detach)"하면, **내 ssh 연결이 끊겨도 세션은 서버에서
계속 돌아간다.** 나중에 다시 접속해서 "붙이면(attach)" 진행 상황을 그대로 이어 본다.

> 비유: 서버 안에 따로 켜 둔 모니터 한 대. 내가 자리를 떠도(연결을 끊어도) 그 모니터 속
> 프로그램은 계속 돌고, 다시 와서 그 모니터를 들여다보면 된다.

> 아래 tmux 명령은 모두 **서버에 ssh로 들어온 상태에서** 친다(내 맥이 아니라 서버 쪽).

### 핵심 흐름 (이 순서만 익히면 됨)

```bash
# 1) (서버에 ssh로 들어온 상태에서) 'work'라는 이름의 새 세션 시작
tmux new -s work
```

이제 들어온 화면 안에서 평소처럼 명령을 친다. 여기서 AF3든 학습 스크립트든 길게 도는 작업을
실행한다. 그 다음:

```text
# 2) 세션에서 빠져나오되 작업은 계속 돌리기 (= 분리, detach)
#    키보드로: Ctrl-b 를 누르고 손을 뗀 다음, 이어서 d 를 누른다
Ctrl-b  그리고  d
```

`Ctrl-b`는 tmux에게 "지금부터 명령이야"라고 알리는 **프리픽스 키**다. `Ctrl`을 누른 채 `b`를
누르고 → 둘 다 떼고 → `d`를 누른다(동시에 누르는 게 아니다). 분리되면 평소 서버 프롬프트로
돌아오고, 화면에 `[detached ...]` 비슷한 메시지가 뜬다. 이 상태에서 ssh를 끊거나 노트북을 닫아도
`work` 세션은 살아 있다.

다시 돌아왔을 때(서버에 다시 ssh로 접속한 뒤):

```bash
# 3) 지금 살아 있는 세션 목록 확인
tmux ls

# 4) 'work' 세션에 다시 들어가기 (= 붙이기, attach)
tmux attach -t work
```

작업이 끝나서 세션을 완전히 정리할 때:

```bash
# 5) 'work' 세션 종료 (그 안의 작업도 함께 끝남)
tmux kill-session -t work
```

> 다시 강조: 종료(`kill-session`)는 안에서 돌던 작업까지 끝낸다. 아직 작업이 도는 중이라면
> 종료하지 말고 **분리(Ctrl-b → d)**만 한다.

### 창(window)·패널(pane) — 아주 간단히

당장 필요하진 않지만, 한 세션 안에서 화면을 더 쪼개고 싶을 때가 있다. 전부 프리픽스 `Ctrl-b`로
시작한다.

- `Ctrl-b` → `c` : 새 **창(window)** 만들기(탭처럼 여러 작업 화면을 둠).
- `Ctrl-b` → `n` : 다음 창으로 이동(`p`는 이전 창).
- `Ctrl-b` → `%` : 현재 화면을 **좌우 패널(pane)**로 분할.
- `Ctrl-b` → `"` : 위아래 패널로 분할.
- `Ctrl-b` → 방향키 : 패널 간 이동.

처음에는 "세션 새로 만들기 / 분리 / 다시 붙이기" 세 가지만 확실히 익히면 충분하다.

> 참고: `tmux`가 서버에 없으면(`command not found`) `screen`이라는 비슷한 도구가 있을 수 있다.
> 개념은 같지만 명령이 다르다(`screen -S work` 새 세션, `Ctrl-a` 다음 `d` 분리, `screen -ls`
> 목록, `screen -r work` 다시 붙기). 둘 다 없으면 멘토에게 어떤 걸 쓰는지 물어본다.

## 4. 공용 서버 에티켓과 주의  (서버 안에서 실행)

연구실 서버는 **여러 사람이 같이 쓰는 공용 자원**이다. 내 작업이 남의 작업을 방해하거나, 실수로
남의 결과를 지우면 큰 사고가 된다. 무거운 작업을 돌리기 전에 아래를 습관화한다. (아래 점검
명령은 서버 안에서 친다.)

### GPU가 비어 있는지 확인: `nvidia-smi`

```bash
nvidia-smi
```

- **무엇:** 서버의 GPU 상태(메모리 사용량, 지금 누가 돌리는지)를 보여 준다. (NVIDIA GPU와
  드라이버가 설치된 서버에서만 동작한다 — 없으면 `command not found`.)
- **왜:** AF3 같은 작업은 GPU를 많이 먹는다. 이미 누군가 GPU를 꽉 채워 쓰고 있으면 내 작업이
  실패하거나, 함께 돌려 둘 다 느려진다. **시작 전에 빈 GPU가 있는지 먼저 본다.**
- 표의 메모리 사용량(예: `Memory-Usage`)이 거의 0이고 GPU 사용률(예: `GPU-Util`)이 낮으면
  여유가 있는 것이다. (컬럼 이름·표기는 드라이버 버전에 따라 조금씩 다를 수 있다.)

### 디스크 여유 확인: `df -h`

```bash
df -h
```

- **무엇:** 디스크(저장 공간)의 전체 용량과 남은 용량을 사람이 읽기 쉬운 단위(`-h`)로 보여 준다.
- **왜:** AF3 결과는 용량이 크다. 디스크가 꽉 차면 나뿐 아니라 **모두의 작업이 멈춘다.** 큰
  결과를 만들기 전에 여유가 있는지 보고, 끝난 결과는 내 맥으로 받은 뒤 서버에서 정리한다.
- 사용률(보통 `Use%` 열)이 90%를 넘어가면 주의하고, 멘토에게 어디에 데이터를 두면 되는지
  물어본다. (서버에는 여러 디스크/마운트가 보일 수 있는데, 내 작업·홈이 어느 줄인지 헷갈리면
  멘토에게 확인한다.)

### 내 프로세스만 다루기

```bash
# 내가 띄운 프로세스 목록 (간단히, 한 번 출력하고 끝)
ps -u <USER>

# 실시간으로 보기 (q 를 누르면 빠져나옴)
top -u <USER>
```

- 남이 돌리는 작업(프로세스)은 **절대 강제 종료하지 않는다.** `kill` 류 명령은 내가 직접 띄운
  것만, 그것도 정말 필요할 때만 쓴다.
- 어떤 작업이 누구 것인지 헷갈리면 건드리지 말고 멘토/동료에게 먼저 확인한다.
- (참고: `top -u`는 리눅스 서버 기준 문법이다. 내 맥에서 `top`을 쓸 일은 거의 없지만, 맥의
  `top`은 옵션이 다르니 위 명령은 서버에서만 쓴다고 생각한다.)

### 위험한 명령 경고: `rm -rf`

```text
rm -rf <경로>     # ← 매우 위험. 함부로 쓰지 말 것
```

- `rm`은 파일 삭제, `-r`은 폴더 안까지 통째로, `-f`는 확인 없이 강제로 지운다는 뜻이다. 합쳐서
  `rm -rf`는 **확인도 안 묻고 폴더를 통째로 영구 삭제**한다. 휴지통도 거치지 않아 복구가 거의
  불가능하다.
- 경로를 한 글자만 잘못 쳐도(예: `~/af3 /old` 처럼 의도치 않은 띄어쓰기) 엉뚱한 곳이 날아간다.
  특히 `rm -rf /` 나 `rm -rf ~` 같은 건 시스템/내 홈 전체를 지우는 재앙이니 **절대 치지 않는다.**
- 폴더를 지워야 한다면: (1) 먼저 `ls <경로>`로 **무엇이 들어 있는지 눈으로 확인**하고,
  (2) 가능하면 `-f` 없이 지워 확인 프롬프트를 받고, (3) 자신이 없으면 멘토에게 물어본다.
- AF3 보조 폴더(`msas/`, `template/`) 정리처럼 반복되는 삭제는, 손으로 `rm -rf` 하기보다
  검증된 스크립트(`scripts/clean_af3_outputs.py`)를 쓰는 편이 안전하다. 이 스크립트는
  **기본이 예행 연습(DRY-RUN)** 이라, `--apply`를 붙이기 전까지는 "무엇을 지울지" 목록만 보여
  주고 실제로는 아무것도 지우지 않는다:

  ```bash
  # 1) 먼저 목록만 확인 (실제 삭제 안 함)
  python scripts/clean_af3_outputs.py ~/af3_runs/complex01
  # 2) 목록이 맞으면 그때 실제 삭제
  python scripts/clean_af3_outputs.py ~/af3_runs/complex01 --apply
  ```

## 5. VSCode Remote-SSH로 서버를 GUI처럼 다루기

### 무엇 / 왜

지금까지는 터미널에서 글자로만 서버를 다뤘다. **VSCode의 Remote-SSH** 확장을 쓰면, 내 맥의
VSCode 창 안에서 **서버의 파일을 GUI 편집기처럼 열어 보고 고치고**, 서버의 통합 터미널까지
바로 쓸 수 있다. 코랩/주피터에서 막 넘어온 입장에선 가장 편하게 적응되는 방법이다.

### 어떻게 (개요)

> 아래 메뉴·명령 이름은 VSCode 버전에 따라 표현이 조금 다를 수 있다(현재/일반적 기준). 정확한
> 항목 이름은 명령 팔레트에서 "Remote-SSH"로 검색하면 바로 나온다.

1. VSCode 확장 탭에서 **Remote - SSH** 확장을 설치한다.
2. 명령 팔레트(`Cmd-Shift-P`)에서 `Remote-SSH: Connect to Host...`(또는 비슷한 항목)를 선택한다.
3. 접속 정보를 한 번 등록해 두면(아래 형식) 다음부터 클릭으로 접속된다. VSCode는 내부적으로
   바로 그 `ssh -p <PORT> <USER>@<YOUR_SERVER_IP>` 정보를 쓴다.

`~/.ssh/config` 파일(내 맥에 있는 ssh 설정 파일)에 아래처럼 별칭을 적어 두면 VSCode 목록과
터미널 양쪽에서 편하다. (들여쓰기는 공백을 쓴다.)

```text
Host lablab
    HostName <YOUR_SERVER_IP>
    Port <PORT>
    User <USER>
```

이렇게 해 두면 터미널에서도 그냥 `ssh lablab` 한 줄로 접속된다(포트·계정을 매번 안 써도 됨).

### 주의

- Remote-SSH로 편집해도 결국 **서버에서 실행**되는 것이다. 무거운 작업은 여전히 §3의 `tmux`
  안에서 돌려야, VSCode 창을 닫아도 작업이 살아 있다. (VSCode 통합 터미널을 닫으면 그 안의
  작업은 죽을 수 있다.)
- VSCode 편집·실행·통합 터미널의 기본 사용법은 `docs/00_VSCode_파이썬_워크플로.md`(추후 작성
  예정)에 정리한다. 여기서는 "그걸 서버에 그대로 연결한다"는 점만 알면 된다.

## 한눈에 보는 명령 모음

```bash
# === 접속 (내 맥에서) ===
ssh -p <PORT> <USER>@<YOUR_SERVER_IP>        # 서버 로그인 (포트는 소문자 -p)
exit                                          # 서버에서 나오기 (또는 Ctrl-d)

# === 파일 전송 (내 맥에서, 포트는 대문자 -P) ===
scp -P <PORT> 로컬파일 <USER>@<YOUR_SERVER_IP>:~/             # 올리기
scp -P <PORT> <USER>@<YOUR_SERVER_IP>:원격파일 .             # 가져오기
scp -r -P <PORT> <USER>@<YOUR_SERVER_IP>:~/af3_runs/x ./x    # 폴더째 가져오기
rsync -avz -e "ssh -p <PORT>" <USER>@<YOUR_SERVER_IP>:~/x ./ # 동기화(이어받기)

# === 장시간 세션 (서버 안에서) ===
tmux new -s work          # 새 세션 시작
# (안에서 작업 실행 후)  Ctrl-b 그리고 d   → 분리(작업은 계속 돎)
tmux ls                   # 세션 목록
tmux attach -t work       # 다시 붙기
tmux kill-session -t work # 세션 종료(안의 작업도 끝남)

# === 서버 상태 점검 (서버 안에서) ===
nvidia-smi                # GPU 사용 현황 (NVIDIA GPU 서버에서만)
df -h                     # 디스크 여유
ps -u <USER>              # 내 프로세스 목록 (한 번 출력)
top -u <USER>             # 내 프로세스 실시간 보기 (q로 종료)
```
