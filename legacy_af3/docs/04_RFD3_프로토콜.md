## 1. RFD3는 무엇이고 무엇을 하나

### 1-1. 한 문장 정의

RFD3는 **"표적 분자(우리 경우 항원)를 정해주면, 거기에 달라붙는 새로운 단백질(binder)의
3차원 구조(백본 + 곁사슬 원자 좌표)를 생성해 주는 AI 도구"**입니다.

- **binder(바인더):** 어떤 표적에 "붙는" 단백질. 우리 맥락에서는 "항원에 붙는 새 단백질" =
  사실상 새 항체/미니단백질 후보라고 생각하면 됩니다.
- **backbone(백본, 뼈대):** 단백질에서 아미노산들을 잇는 주사슬의 3차원 골격. RFD3는 "이런 모양으로
  접히면 표적에 붙겠다"는 **3차원 모양(구조)을 만드는 것이 핵심**이고, **그 자리에 어떤 아미노산을
  넣을지(서열)는 다음 단계 도구**에 맡깁니다. (서열 단계는 §7)
  - 참고: RFD3는 사실 곁사슬 원자까지 포함한 **all-atom(모든 원자) 좌표**를 만들어 냅니다. 다만 이때
    함께 따라오는 아미노산 서열은 **아직 최적화된 것이 아니어서**, 그래서 §7에서 전용 서열 설계
    도구로 서열을 다시 정하는 단계가 필요합니다. (= "모양은 거의 다 정해졌고, 서열은 다음 단계에서
    제대로 채운다"고 이해하면 됩니다.)

### 1-2. "diffusion(디퓨전)"이 뭔지 — 비유 한 문장

RFD3의 "diffusion"은 **"처음엔 완전히 흐릿한(노이즈투성이) 점 구름에서 시작해, 노이즈를 조금씩
지워 가며 점점 또렷한 단백질 구조로 만들어 가는 방식"**입니다.
마치 **모래가 마구 섞인 상태에서 흔들기를 반복하며 점점 모양 있는 조각상으로 다듬어 가는 것**에
가깝다고 생각하면 됩니다. (이미지 생성 AI가 노이즈에서 그림을 만들어 내는 것과 같은 원리입니다.)

### 1-3. 기존 RFdiffusion / RFdiffusion2와의 관계 (한 줄)

RFD3는 RFdiffusion(1)·RFdiffusion2의 후속(3세대)으로, **모든 원자 수준(all-atom)에서 단백질·핵산·작은
분자와의 상호작용까지 한 모델로 설계**하며, 결과를 배치(묶음)로 생성해 RFD2 대비 약 10배 빠르다고
보고됩니다. RFD1·RFD2의 발전형이지만, RFD3는 **foundry라는 새 패키지에서 새 명령·새 설정 형식으로
돌리는 새 모델**이라 **이전 버전 사용법(명령어·설정)이 그대로 통하지 않습니다.**
(← 그래서 옛날 RFdiffusion 튜토리얼을 그대로 따라 하면 안 됩니다.)

### 1-4. 공식 출처 (반드시 여기서 최신본 확인)

- 공개 발표: Institute for Protein Design(IPD) / Rosetta Commons,

- 튜토리얼 공개: "RFD3 Tutorials Are Here!" (Rosetta Commons, 2026-03)

  bioRxiv / PMC 2025
- 코드·문서: Rosetta Commons **foundry** 저장소(GitHub `RosettaCommons/foundry`)의 `models/rfd3`
  및 foundry 문서 사이트(`rosettacommons.github.io/foundry`)의 RFdiffusion3 튜토리얼

> 위 위치·이름·버전(작성 시점 foundry 0.1.x)도 바뀔 수 있으니, "RFdiffusion3",

## 2. 전체 작업 흐름 한눈에

```
[표적(항원) 구조 PDB 준비]
        │   (어디에 붙일지 = 핫스팟 잔기 지정)
        ▼
[RFD3 실행]  ──►  설계된 binder 구조 여러 개 (.cif.gz 등 구조 파일)
        │
        ▼
[서열 설계: ProteinMPNN / LigandMPNN]  ──►  각 백본에 들어갈 아미노산 서열
        │
        ▼
[검증: RF3(RoseTTAFold3)·AF3 등으로 다시 접어보기 / 우리 docking 평가]
        │
        ▼
[상위 후보 선별]  ──►  cloning → wet 실험 검증 (멘토 실무 흐름)
```

핵심: **RFD3는 "모양(구조)"을 만든다.** 그 모양에 최적화된 서열을 입히고(§7), 그 서열이 정말 그
모양으로 접혀 표적에 붙는지 검증하는 단계가 뒤따릅니다. 우리 프로젝트에서는 그 검증·선별에 **여러
docking 모델의 합의(consensus) 평가**가 들어갑니다(§8).

## 3. 1단계 — 환경(실행 환경) 준비

"환경"이란 RFD3가 돌아가는 데 필요한 파이썬 패키지·라이브러리·모델 가중치(checkpoint)가 갖춰진
**한 벌의 작업 공간**을 말합니다.

> 참고: 작성 시점 공식 문서는 **pip 기반(foundry 패키지)** 설치를 안내합니다. conda나 Docker는 공식
> 문서에 명시돼 있지 않지만, 연구실 서버는 관리 편의상 conda 환경이나 Docker 컨테이너 안에 깔아 둔
> 경우가 많습니다. 어떤 방식인지는 **서버 관리자/멘토에게 확인**하세요.
> - **conda 환경:** 파이썬 패키지들을 한 묶음(가상환경)으로 깔아두고 켜서 쓰는 방식.
> - **Docker(도커) 컨테이너:** "필요한 모든 것이 이미 들어 있는 통째 상자"를 받아서 그 안에서 실행하는
>   방식. 설치 충돌이 적어 서버에서 자주 씁니다.

### 3-1. 가장 먼저 할 일: "이미 깔려 있는지" 확인

연구실 서버에는 **이미 RFD3가 설치돼 있을 가능성이 높습니다.** 새로 깔기 전에 멘토/선배에게 물어보고,
다음을 확인하세요.

- RFD3가 깔린 **경로**와 **켜는 방법**(예: 어떤 conda 환경 이름을 켜야 하나, 어떤 도커 이미지를 쓰나)
- **모델 체크포인트(checkpoint) 파일 위치** — "checkpoint(체크포인트)"는 학습이 끝난 AI 모델의
  **가중치 파일**(실제 "두뇌")입니다. 이게 있어야 RFD3가 돌아갑니다. 보통 용량이 커서 서버 어딘가에
  공용으로 받아둡니다.

```bash
# (예시) conda 환경 목록 보기 — 이름에 rfd / rfdiffusion / foundry 등이 있는지 확인
conda env list

# (예시) 도커 이미지 목록 보기 (도커로 깔려 있을 때)
docker images

# (예시) 명령이 PATH에 잡혀 있는지 확인 (환경을 켠 뒤)
which rfd3 || echo "rfd3 명령이 안 잡힘 → 환경부터 켜거나 설치 경로 확인 필요"
```

### 3-2. (참고) 공식 설치 형태 — 단정 금지, 예시일 뿐

작성 시점 공식 foundry 문서 기준 설치는 대략 아래 형태입니다(**버전에 따라 다를 수 있어 그대로 믿지
말 것**).

```bash
# (예시) 패키지 설치 — RFD3만
pip install "rc-foundry[rfd3]"
# (참고) 여러 모델을 함께 쓰려면 공식 README의 "rc-foundry[all]" 등 안내를 따른다.

# (예시) 모델 체크포인트 내려받기
foundry install rfd3 --checkpoint-dir <체크포인트를_저장할_경로>
```

> - 위 명령은 **작성 시점 공식 문서 기준 예시**이며, 패키지명·옵션이 바뀌었을 수 있습니다.
> - 수소결합(H-bond) 조건을 쓰려면 별도 도구(HBPLUS) 설치가 추가로 필요하다고 공식 문서가 안내합니다
>   (처음 기본 binder 설계에는 보통 필요 없음).
> - 실제 설치는 서버 관리자/멘토 안내를 따르세요. 초보자가 직접 설치까지 할 일은 보통 없습니다 —
>   **"켜서 쓰는 법"만 익히면 충분**한 경우가 많습니다.

## 4. 2단계 — 입력 준비 (표적 구조 + 조건 지정)

RFD3에 넣어야 하는 입력은 크게 두 가지입니다.

1. **표적(항원) 구조 파일** — 보통 `.pdb` 파일.
2. **"어떻게 설계할지" 조건** — 어디에 붙일지(핫스팟), binder 길이 등. 보통 **설정 파일(YAML)**에
   적습니다.

### 4-1. 표적 구조 PDB

- **PDB 파일:** 단백질의 원자 좌표가 적힌 표준 텍스트 형식. 표적 항원의 3차원 구조입니다.
- 출처: 실험 구조(예: PDB 데이터베이스에서 받은 것) 또는 AF3로 예측한 구조 등.
- 표적에서 **필요 없는 부분(다른 사슬, 물 분자 등)은 미리 정리**하는 경우가 많습니다(전처리).

### 4-2. 핫스팟(hotspot) 잔기 — "여기에 붙어라" 지정

- **핫스팟(hotspot):** 표적 표면에서 **"binder가 꼭 닿았으면 하는 잔기들"**. 이걸 지정해야 RFD3가
  표적의 아무 데나가 아니라 **우리가 원하는 부위(예: 항원의 특정 에피토프)**에 붙는 binder를 만듭니다.
  공식 튜토리얼에 따르면 "RFD3는 핫스팟이 binder의 어떤 무거운 원자로부터 보통 4.5 Å 이내에 오도록
  학습되었다"고 합니다.
- 개수는 공식 문서가 딱 정해 두지 않았습니다. 다만 일반적으로 **몇 개(예: 3~6개) 정도**의 핵심 잔기를
  고르는 것이 무난합니다(너무 적으면 엉뚱한 데, 너무 많으면 과한 제약). **정확한 권장은 현재 튜토리얼
  확인.**
- 표기는 보통 `사슬기호 + 잔기번호` 형태입니다(예: 사슬 E의 64번 → `E64`).

### 4-3. 설정 파일(YAML) 개요

조건들은 텍스트 설정 파일(YAML)에 적습니다. **아래는 작성 시점 공식 PPI 튜토리얼의 키 이름을 옮긴
"형태 예시"이며, 키 이름·구조는 버전에 따라 달라질 수 있습니다.**

```yaml
# (예시) ppi_input.yaml — 단백질-단백질 binder 설계용. 실제 키는 공식 문서로 확인할 것.
input: /경로/표적_정리본.pdb        # 표적(항원) 구조 (PDB)
contig: 40-120,/0,E6-155            # 설계할 영역 / 사슬 끊김 / 보존할 사슬 지정 (아래 설명)
length: 190-270                     # 최종 구조 전체 잔기 수 범위
select_hotspots:                    # 핫스팟 잔기들 (사슬+번호 → 닿을 원자들)
  E64: CD2,CZ
  E88: CG,CZ
  E96: CD1,CZ
infer_ori_strategy: hotspots        # binder를 핫스팟 쪽으로 배치하는 전략
is_non_loopy: true                  # 루프(헐렁한 고리)를 줄이도록 (PPI 설계에 권장)
```

- **contig(콘티그):** "어느 부분을 새로 설계하고, 어디서 사슬을 끊고, 어느 사슬을 그대로 둘지"를 적는
  표기. 예: `40-120`은 "40~120개 잔기 길이의 새 binder를 설계", `/0`은 "사슬 끊김(체인 브레이크)",
  `E6-155`는 "표적 사슬 E의 6~155번은 그대로 둔다"는 식입니다(정확한 문법은 버전별 공식 문서 확인).
- **length:** 만들 구조의 전체 잔기 수 범위.
- **select_hotspots:** §4-2의 핫스팟(잔기 → 닿을 무거운 원자 이름들).
- **infer_ori_strategy / is_non_loopy:** PPI(단백질-단백질 계면) 설계에서 자주 쓰는 옵션
  (배치 전략 / 루프 억제). **버전에 따라 키 이름·기본값이 다를 수 있음.**

> 핫스팟 표기는 위 `select_hotspots`(YAML) 방식 외에, 구버전류에서는
> `ppi.hotspot_res=[A30,A33,A34]`처럼 다른 형식으로 쓰기도 합니다 — **반드시 현재 버전 문서로 확인**.

## 5. 3단계 — 실행

### 5-1. 실행 명령의 일반적 모양 (예시 — 단정 금지)

작성 시점 공식 foundry 튜토리얼 기준, RFD3 실행은 `rfd3 design ...` 형태입니다.

```bash
# (예시) 그대로 외우지 말고, 서버에 깔린 버전·공식 튜토리얼로 확인할 것
rfd3 design \
  out_dir=outputs/run0 \
  inputs=ppi_input.yaml \
  ckpt_path=/경로/체크포인트/rfd3_latest.ckpt
```

- `out_dir` : 결과를 저장할 폴더
- `inputs`  : §4에서 만든 설정 파일(YAML)
- `ckpt_path` : 모델 체크포인트(§3-1에서 확인한 가중치 파일) 경로

> 실제 키 이름(`out_dir`/`inputs`/`ckpt_path` 등)은 버전마다 다를 수 있습니다. 설계 개수는
> `diffusion_batch_size`(한 배치당 디자인 수)·`n_batches`(배치 수)로 조절하며, 지정하지 않으면
> 기본값이 적용됩니다(튜토리얼 기본은 디자인 8개).

### 5-2. 서버에서 돌릴 때 실무 팁

- **시간이 오래 걸리고 GPU를 씁니다.** 접속이 끊겨도 계속 돌게 하려면 `tmux`(또는 `nohup`)로 띄우세요
  (→ [`03_서버_ssh_scp_tmux.md`](03_서버_ssh_scp_tmux.md)).
- **먼저 적은 수(예: 4~8개)로 "파일럿(pilot) 실행"**을 해서, 핫스팟·길이 설정이 의도대로 나오는지
  확인한 뒤 대량 생성으로 넘어가는 것이 정석입니다.
- GPU 사용 현황은 `nvidia-smi`로 확인할 수 있습니다(메모리·다른 사람 작업 점유 여부).

## 6. 4단계 — 출력 보기 (설계된 구조들)

- 출력은 보통 `out_dir`에 **설계된 구조 파일**(압축된 CIF, 예: `..._model_0.cif.gz` …)과
  **실행 정보가 담긴 JSON**으로 떨어집니다. 튜토리얼 기본 설정에서는 디자인 8개(0~7번),
  이름은 대략 `<설정이름>_<n>_model_<m>.cif.gz` 형태로 보고됩니다(**정확한 개수·이름 규칙은
  버전·설정마다 다름**).
- **CIF/PDB 파일:** 단백질 3차원 좌표 파일. PyMOL 등 구조 뷰어로 열어 봅니다(→ AF3 결과 보기와
  비슷, [`02_AF3_출력_처리.md`](02_AF3_출력_처리.md) 참고).
- 디자인 1개 = "표적에 붙을 binder **구조 하나**"입니다. 보통 여러 개를 만들어 두고 다음 단계에서
  거릅니다.

```bash
# (예시) 결과 폴더 살펴보기
ls -lh outputs/run0
# .cif.gz 가 보이면, 압축을 풀거나(gunzip -k 파일.cif.gz) 뷰어로 바로 열어 확인
```

> `gunzip -k`의 `-k`는 "원본(.gz)을 지우지 말고 유지(keep)"하라는 옵션입니다. 압축 파일을 남겨 두면
> 안전합니다.

## 7. 5단계 — RFD3 다음: 서열 설계·검증으로 이어지기

RFD3 출력은 **"모양(구조)"까지**입니다(곁사슬 좌표는 있지만 서열은 아직 최적화 전). 실제 쓸 수 있는
단백질이 되려면 다음이 필요합니다.

1. **서열 설계 (ProteinMPNN / LigandMPNN):**
   - **ProteinMPNN:** "이 3차원 백본에는 어떤 아미노산 서열이 들어가야 이 모양으로 안정적으로
     접힐까?"를 채워 주는 도구. RFD3가 만든 백본에 **아미노산을 입히는 단계**입니다.
   - 표적에 DNA·리간드·금속 같은 비-단백질 파트너가 있으면 **LigandMPNN**(ProteinMPNN의 확장)을
     쓰는 것이 공식 권장입니다. 순수 단백질-단백질이면 ProteinMPNN으로 충분합니다.
   - 백본 하나당 서열 후보를 여러 개 뽑는 것이 보통입니다.
2. **검증(다시 접어보기):**
   - 뽑은 서열을 **구조 예측기로 다시 예측**해서, "그 서열이 정말 우리가 의도한 모양으로 접히고
     표적에 붙는가?"를 확인합니다. (이를 흔히 "self-consistency / 재접힘 검증"이라 부릅니다.)
   - 공식 IPD 파이프라인은 검증에 **RF3(RoseTTAFold3)**를 씁니다. 우리 프로젝트에서는 이미 **AF3**를
     쓰고 있으므로, 여기서 **AF3 항체-항원 docking + 우리 보강 ML 평가**로 이어집니다(§8).

> 즉 전체는 **RFD3(구조) → ProteinMPNN/LigandMPNN(서열) → RF3·AF3·docking(검증)**의 릴레이입니다.
> RFD3만으로 끝나지 않는다는 점을 꼭 기억하세요. (이 후속 도구 권장은 일반 관행 + 공식 IPD 파이프라인
> 기준이며, 세부 권장 도구는 현재 공식 문서로 확인하세요.)

## 8. 우리 메인 파이프라인과의 연결

우리 메인 프로젝트는 **AF3 항체-항원 docking을 보강하는 ML 프레임워크**입니다. RFD3는 그 앞단에서
"검증할 후보를 만들어 주는 공급원" 역할로 붙습니다. 연결 흐름은 다음과 같습니다(개념적 연결 — 멘토와
실제 기여 범위·발표 구성을 맞춰야 함).

```
RFD3로 binder 후보 구조 생성
        │  (+ ProteinMPNN/LigandMPNN 서열)
        ▼
각 후보를 "여러 docking 모델"로 평가  ──►  consensus(합의) 점수 계산
        │   (AF3 + 비-AF3 docking, 그리고 우리 ML 보강 점수)
        ▼
상위 후보 선별  (ipTM만 보지 않고, 계면 기하·PLM 임베딩 기반 보강 지표로 묻힌 좋은 포즈 구제)
        │
        ▼
cloning → wet 실험 검증
```

- **consensus docking(합의 도킹):** 한 모델 결과만 믿지 않고 **여러 도킹 방법의 결과를 모아 합의가
  높은 후보를 신뢰**하는 전략. 우리 메인 프로젝트의 척추(멘토 실무 #2)와 직결됩니다.
- 우리 ML 보강 도구는 이 선별 단계에서 **AF3의 전역 ipTM이 놓치는 "계면의 국소 상보성"을 잡아**
  좋은 binder 후보가 낮은 ipTM 때문에 버려지는 것을 줄이는 역할을 합니다.
- 최종 상위 후보는 **cloning → 단백질 발현·정제 → 기능 검증** 같은 wet 실무로 이어집니다
  (멘토 실무 흐름; cloning 등 wet 단계는 이 문서 범위 밖이며, 별도 wet 안내/문서를 참조).

> 정리: **RFD3 = 후보 생성기**, **우리 ML 프레임워크 = 후보 선별 보강기**, **wet = 최종 검증**.
> 한 스토리로 묶으려면 "RFD3 후보를 consensus + 보강 ML로 선별해 wet으로 넘긴다"는 연결고리를
> 멘토와 먼저 맞춰야 합니다(아직 확정 전 — 멘토 확인 필요).

## 부록. 용어 빠른 사전

- **binder:** 표적에 붙는 단백질. 우리 맥락에선 "항원에 붙는 새 단백질 후보".
- **backbone(백본):** 단백질 주사슬의 3차원 골격(RFD3는 곁사슬 원자 좌표까지 만들지만, 서열은 아직
  최적화 전).
- **diffusion(디퓨전):** 노이즈에서 시작해 점점 다듬어 구조를 만드는 생성 방식.
- **hotspot(핫스팟):** 표적 표면에서 binder가 닿길 바라는 잔기들(설계 부위 지정).
- **contig(콘티그):** "어디를 새로 설계하고, 어디서 끊고, 어디를 보존할지" 적는 설정 표기.
- **checkpoint(체크포인트):** 학습 끝난 모델의 가중치 파일(실제 "두뇌").
- **conda / Docker:** 실행 환경을 갖추는 두 방식(가상환경 / 통째 상자).
- **ProteinMPNN / LigandMPNN:** RFD3가 만든 백본에 아미노산 서열을 입히는 도구(서열 설계).
  비-단백질 파트너가 있으면 LigandMPNN.
- **RF3(RoseTTAFold3) / AF3:** 설계한 서열이 의도한 구조로 접히는지 다시 예측해 검증하는 도구.
- **consensus docking:** 여러 도킹 결과의 합의로 신뢰 높은 후보를 고르는 전략.
